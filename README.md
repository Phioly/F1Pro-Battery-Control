# F1Pro EC Control

SteamOS（Decky Loader）下的 OneXFly F1 Pro / HX 370 掌机 EC 控制插件。

覆盖两组功能：**充电控制**（旁路供电开关 + 充电上限）与 **风扇控制**（五档模式 + 自定义温度曲线）。

> 仓库：<https://github.com/Phioly/F1Pro-EC-Control>
>
> **旧名 `F1 Pro Battery Control` 已改名。** Decky 会把新旧两份当成两个不同的插件，
> 升级时请先按文末「从旧版本升级」一节卸载旧插件。

**当前版本**：`v0.6.11` · **适用**：SteamOS + Decky Loader · **不涉及** TDP / CPU 调度（可与 SimpleDeckyTDP 共存）

**只想装上用**？直接看 [安装](#安装) → [从旧版本升级](#从旧版本升级重要)。
**遇到问题**？先看 [故障排查](#故障排查)，再看 [日志位置](#日志位置)。

## 功能

| 功能 | 写入的内核值 | 说明 |
| --- | --- | --- |
| 🔋 正常充电 | `auto` | 正常充电，并遵循充电上限 |
| ⚡ 开机旁路 | `inhibit-charge-awake` | 唤醒时停止充电、由电源直接供电；**进入睡眠 / 关机后解除该抑制，接电照常充电并遵循充电上限**（F1 Pro oxpec 驱动的具体行为，见下） |
| 🔌 始终旁路 | `inhibit-charge` | 运行、睡眠、关机都不充电，适合长期插电 |
| 🔢 充电上限 | `charge_control_end_threshold` | 50 / 60 / 70 / 80 / 85 / 90 / 95 %，另有「不限制」 |
| 🌀 风扇控制 | `oxp_ec` 的 `pwm1` / `pwm1_enable` | 自动 / 静音 / 均衡 / 性能 / 自定义，五点（温度→PWM）曲线 |
| ♻️ 启动恢复 | — | Decky 启动时重新应用上次保存的模式、上限与风扇模式（可关闭） |
| 🔔 错误提示 | — | 仅操作失败时弹出通知；成功切换静默无提示 |

> 版本：**v0.6.11**。
>
> **v0.6.11** 再补**四处异常时序缺口**（**电池部分一行未改**），顺序依旧是
> **离线探针先复现 → 补回归测试 → 最后改实现**。四处共同点是：
> **正常路径、单次调用、测试全绿时都看不出来，只有"卸载超时""线程没停干净"
> "RPC 被拒绝"这类失败路径才露出来**。
>
> ① **卸载取锁超时后，在途的 RPC 仍会把控制权抢回手动**。
> v0.6.10 的世代号只能作废"**在途的那一步**"（`_fan_step()` 内部），
> 挡不住一次 RPC 转换在它**之后的步骤**：`_fan_apply_manual()` 在
> `_fan_step()` 返回后还会 `_start_fan_controller()` 并 `return True`，
> `_set_fan_mode_sync()` 随后报 `ok=True`。离线探针复现：卸载取锁超时 →
> 走"仍尝试交还 EC"的分支并返回（当时 EC 已是自动）→ 那个 RPC 从 I/O 里
> 出来继续往下走 → **卸载已经结束，EC 却变回手动，而且报告成功**。
> 修法：`_unload()` 在**取走控制权那一刻**（取锁**之前**）置位 `_fan_unloading`，
> 此后 `_fan_step()` 不再自动夺权、`_fan_apply_manual()` / `_set_fan_mode_sync()`
> 也在返回成功前检查它 —— 整段转换作废，而不只是那一步。
>
> ② **保存自定义曲线仍没检查控制线程启动失败**。
> `_set_fan_mode_sync()` 那条路径在 v0.6.10 已修好，但
> `_set_fan_custom_curve_sync()` 在自定义模式下调用 `_start_fan_controller()`
> 后**直接返回 `ok=True`**。离线探针复现：旧线程还没退出时保存曲线报告成功，
> 却**没有任何控制循环** —— 风扇不跟温度走、85 °C 保护也失效，
> 比直接交还 EC 危险得多。现在起不来即抛错，由调用方兜底交还 EC。
>
> ③ **前端：切换失败会丢掉未保存的本地编辑**。
> `changeFanMode()` 原先在 RPC **成功之前**就把预设曲线填进滑杆、
> 清掉 `curveTouched` 与 `curveDirty`。于是切换失败时曲线已被换成预设值、
> 「保存为自定义并应用」按钮直接变灰 —— **用户在滑杆上的修改没有任何提示地消失**。
> 修法：整段状态覆盖挪到 `await` 成功之后。
>
> ④ **前端：轮询不捕获 RPC 异常**。
> 轮询 `tick` 只有 `finally`、没有 `catch`，`getStatus()` 一旦被拒绝就产生
> 一次未处理的 Promise rejection，而且**下面读风扇状态的代码被整段跳过**。
> 两者是独立的 RPC，电池读失败不该把风扇状态一起拖下水。修法：两段各自
> `try/catch`（只记原因、不弹通知 —— 5 秒一轮会刷屏），续排仍放 `finally`。
>
> 测试：后端 **237 → 273 项**（新增第 18 节「卸载取消在途 RPC / 保存曲线必须
> 检查启线程结果」，含**只用卸载标志就能拦住的夺权场景**直测与反向对照；
> 另有每个场景结束时的**「不得留下仍在运行的控制线程」守卫**）、
> 前端 **156 → 166 项**（新增「切模式失败不得丢编辑 / 轮询必须自己吞掉 RPC 异常」）。
> 变异：后端 **17 → 20 条**、前端 **21 → 23 条**，**全部干净报 FAIL**。
>
> 本轮变异又抓到**两处需要修的东西**（都不是被测行为，而是验证本身的缺陷）：
> - **M19 原先是个"等价变异"**：它把 `_fan_cancelled(epoch)` 换回
>   `_fan_step_invalidated(epoch)`，但紧随其后的独立 `if self._fan_unloading:`
>   还在 —— 删了等于没删，**它逃逸是"正确"的**。改成真正删掉整段卸载检查后，
>   又暴露出**原断言只覆盖了"世代号也能拦住"的那条路径**（那个场景里
>   `_fan_step_invalidated` 自己就拦住了，卸载标志只是第二重保险），
>   于是"删掉卸载标志检查"仍然只让**日志计数**变红 —— 那是假绿。
>   现在补了一条**只靠卸载标志拦截**的直测（EC 自动 + 世代号有效 + 只置位
>   `_fan_unloading`），并配反向对照。
> - **N25 / N31 原先是"测试崩溃"型变异**：把 `try {` 改成 `{`（或只删
>   `catch`/`finally`）会留下孤立的 `catch`，抽取后 `new Function` 直接
>   `SyntaxError` —— 那算"测试崩溃"而不是"干净报 FAIL"，属于脆写法。
>   现在改成**语法自洽**的替换（整块删掉 `finally`、整段换成无 `try` 版本）。
>
> 顺带修了一处**验证夹具自身的损坏**：`.mut/main.py.orig` 曾被一次被中断的
> 变异跑快照成了"已注入变异"的状态（`_fan_handover_to_ec()` 里多出一句重复的
> `_stop_fan_controller()`、且 `try:` 内缺 `_require_fan_support()`）。
> 结果是**变异脚本的"还原"会把坏版本写回去**。已修好 `main.py` 与
> `.mut/main.py.orig` 并确认两者一致 —— 这也说明**变异脚本的预检值得保留**：
> 它这次直接报出了 M1/M2 找不到原文。
>
> 另外修了**后端测试夹具的清理缺陷**（由用户复查指出，原先表现为
> `npm run test:all` 偶发 `PermissionError: [WinError 32]`）：
> 第 18 节有夹具起了控制线程却**没在场景结束前停掉**，而下一个场景第一件事就是
> `reset_settings()` 删设置文件 —— 后台线程恰好持着该文件句柄时 unlink 就失败。
> **这个失败是竞态**（有时过、有时不过），所以"重跑一次就过了"会把真实缺陷
> 掩盖成"偶发"。两点根因一起修：
> - 新增 `isolated_settings(plugin, tmp)`：给每个场景**独占的设置目录**
>   （`Plugin._settings_path` 是实例属性，可直接注入）。原先所有夹具与它们的
>   后台线程共用同一个全局设置文件，既放大文件锁、又造成跨场景污染；
> - 新增 `teardown_plugins(*plugins)`：置停止标志 → 调 `_stop_fan_controller()`
>   → **必要时再 join 等它真退出**，确认干净后才允许删临时目录。
>
> 同时补了一条**确定性**守卫：`main()` 在每个场景跑完后检查
> `assert_no_leaked_threads()`（扫 `threading.enumerate()` 里以 `F1Pro` 开头的线程）。
> 这样"忘了收尾"会**每次**都红，而不必赌它撞文件锁。验证：修复前该断言
> 稳定红（`plugin_d2` 泄漏）、修复后连续 **10 次全过**；再把 teardown 拿掉，
> 断言**必然**变红 —— 证明它不是空转。
>
> **v0.6.10** 补三处**异常时序下的安全缺口**（**电池部分一行未改**），
> 全部由离线探针先复现、再补测试、最后改实现。共同点是：
> **正常路径都对，只有在"停止线程超时"或"并发交错"时才会露出问题**。
>
> ① **卸载与模式转换必须串行化，且作废在途的那一步**。
> 原先前一步的修复只保证了"两个 RPC 之间"互斥，`_unload()` 自己却不在转换锁里，
> 而且交还 EC 时不看停线程的结果。离线探针复现：控制线程卡在 sysfs 读写里时，
> 卸载写完 `pwm1_enable=2` 就返回了，**排队中的那一步随后恢复执行** ——
> 它读回发现"不是手动"，于是走进夺回控制权的分支，把 `pwm1_enable` 又写回 1。
> 现象是：**卸载已经返回、EC 也曾交还自动，风扇随后却停在手动 PWM 上**。
> 修法有三层，缺一不可：
> - `_unload()` 在**转换锁**里交还（带超时，取不到也继续，不挂住卸载流程）；
> - `_fan_step()` 引入**世代号**：进入时记下当时的值，每次写节点**之前**再比对，
>   只要中间发生过"取走控制权"（停线程 / 交还 EC）就整体作废、一个字都不写；
> - 控制线程等转换锁时**盯着停止标志**，一收到停止请求就放弃这一步。
>   （否则会出现"交还的一方拿着锁等线程退出、线程却在等它放锁"的循环等待，
>   只能靠 join 超时才挣脱 —— 于是一次本来正常的转换被误判成失败。）
> 交还路径仍然会写出 `pwm1_enable=2`（EC 停在手动且无人控制更危险），
> 但只要线程没停干净就**如实返回失败**，让调用方走失败分支。
>
> ② **启动控制线程失败必须算转换失败**。`_start_fan_controller()` 已经会正确
> 返回 `False`（旧线程没停干净时拒绝再起一个），但 `_fan_apply_manual()`
> 忽略了这个返回值、照样返回 `True`。离线探针复现：RPC 得到 `ok=True`、
> 设置与 EC 都是手动模式，**却没有任何控制循环** —— 风扇不跟温度走、
> 85 °C 保护也失效，比直接交还 EC 危险得多。现在起不来即判失败，
> 由调用方兜底交还 EC（并检查交还是否真的成功）。
>
> ③ **曲线「保存」成功、但「应用」失败时不得清掉未保存标记**。
> 「保存为自定义并应用」是两步：先落盘、再切到自定义模式才真正生效。
> `setCurveDirty(false)` 原先夹在两步之间，于是第二步失败时按钮立刻变灰、
> 看起来一切就绪，而 EC 还在跑旧模式 —— 用户连重试的入口都没有了。
> 修法：`changeFanMode()` **回传成败**（原先把异常吞掉只弹通知，调用方无从判断），
> `saveCurve()` 只在回传成功之后才清标记，失败时保持可点并给出可见原因。
>
> 测试：后端 **217 → 237 项**（新增第 17 节「卸载串行化 / 启动失败必须算转换失败 /
> 交还需如实报失败」，含三条**求值验证**：交还落在步骤中途时该步必须作废（两个写入点分别构造）、
> 停线程超时后切手动必须报失败且 EC 回到自动、线程没停干净时交还必须返回 `False`）；
> 前端 **148 → 156 项**（新增「未真正生效前不得清掉未保存标记」节）。变异：后端 **12 → 17 条**、
> 前端 **19 → 21 条**，**全部干净报 FAIL**。
>
> 变异验证时**抓到过一处假绿**：M16（去掉交还返回值里的 `and stopped`）原先指向的断言是
> "停线程超时后切手动必须报告失败"，而那条走的是 `_fan_apply_manual` 返回 `False` 的分支，
> 与交还的返回值**无关** —— 所以把 `and stopped` 去掉照样绿。现在 M16 指向**专门测交还返回值**
> 的那条新断言，并补了反向对照（线程能正常停下时必须报成功，防止"永远返回 False"的坏实现骗过去）。
>
> 顺带修了夹具自身的两处问题（不是被测行为）：第 16 节的两处 `Barrier(2)`
> 会被控制线程重复进入，造成"控制线程等 op2、op2 却在 join 控制线程"的
> 循环等待（改用**一次性**放行）；以及每轮遗留的控制线程会继续写设置文件，
> 让下一轮 `reset_settings()` 撞上 Windows 的文件占用。
>
> **v0.6.9** 修**三处并发 / 生命周期缺陷**（外加一处刷新时序覆盖），
> 全部由离线探针先复现、再补测试、最后改实现（**电池部分一行未改**）。
> 共同点是：**单次调用各自都对，并发或超时之后就不对了**。
>
> ① **新增一把"风扇转换锁"**（`_fan_transition_lock`，`threading.RLock`）。
> 原先只有 `_fan_lock`，它**只保护控制线程对象的创建**。两个 RPC
> （`set_fan_mode` / `set_fan_custom_curve`）各自跑在 `asyncio.to_thread()`
> 的工作线程里，快速连点「切手动 → 存曲线 → 切回自动」时会互相穿插：
> 一个刚写入手动、另一个马上交还 EC，**最终 EC 停在手动而设置文件写着 auto**
> （离线探针 `.mut/repro_fan_concurrency.py` 实测复现出
> `enable=1 → enable=2 → enable=1 → pwm1=138` 这种交错）。
> 现在整段转换都在这把锁里：**停线程 → 取/交控制权 → 写 `pwm1_enable` →
> 写 `pwm1` → 读回验证 → 更新设置 → 启线程**；控制循环的**单步 `_fan_step()`
> 也拿同一把锁**，否则线程会在某个 RPC 转换的中途插进来写 `pwm1`。
> 必须是**可重入**的（RLock）：转换内部的 `_fan_handover_to_ec()` 会调
> `_stop_fan_controller()`、`_fan_apply_manual()` 会调 `_fan_step()` 与
> `_start_fan_controller()`，它们都要拿同一把锁，普通 `Lock` 会自死锁。
>
> ② **控制线程停止超时后不再"假装停掉了"**。`_stop_fan_controller()` 原先
> `join(timeout≈4s)` 之后**无条件清空 `_fan_thread`**。若线程还活着（真机 sysfs
> 读取阻塞时完全可能），下一次操作会认为"没有旧线程"而**再起一个** ——
> **两个线程同时写风扇 PWM**。现在超时后**保留引用**并返回 `False`；
> `_start_fan_controller()` 在旧线程仍活着且已请求停止时**拒绝启动**并记
> error 日志（离线探针 `.mut/repro_fan_concurrency.py` 的 probe_b 复现过
> "丢掉存活线程并起第二个"）。
>
> ③ **前端五个 busy 函数全部补 `try / catch / finally`**。
> `changeMode` / `changeThreshold` / `changeAutoRestore` / `changeFanMode` /
> `saveCurve` 原先只有 `try` + `catch`，**`setBusy(false)` 写在 `try` 末尾**。
> RPC Promise 一被拒绝（`await` 直接抛），恢复语句就永远执行不到，按钮
> **永久禁用**（离线探针 `.mut/repro_busy.mjs` 喂 rejected RPC，实测 4/4 卡在
> busy=true）。现在统一为 `setBusy(true) → try { … } catch { … }
> finally { setBusy(false) }`，异常时也必然恢复。
>
> ④ **保存自定义曲线后不再被默认曲线覆盖**。后端 `get_fan_profiles()` 原先
> 只给预设和 `custom_seed`，而 `profiles` 里**没有 `"custom"` 这个键**，
> 于是前端 `profiles[mode] ?? custom_seed` 在自定义模式下**必然退回默认种子** ——
> 刚保存的曲线会被默认曲线盖掉。现在后端**多返回一个 `custom_curve`**
> （取当前已保存的真值），前端自定义模式**优先取它**；
> `saveCurve()` 成功后**以 RPC 返回的 `result.data.curve` 作为唯一 UI 来源**，

## 前提条件

插件依赖标准 Linux `power_supply` 接口：

```bash
cat /sys/class/power_supply/BAT0/charge_behaviour
```

F1 Pro 上正常应输出类似：

```text
auto inhibit-charge [inhibit-charge-awake]
```

方括号内是当前生效值。若这条命令报"没有那个文件"，说明当前内核没有提供充电控制驱动，
插件会在界面顶部直接提示，而不会静默失效。

### 语义边界：内核 ABI 说什么，F1 Pro 具体怎么做

这一段很重要，因为两者**不是一回事**，混在一起会得出错误结论。

**① 内核 ABI 的通用定义**（`Documentation/ABI/testing/sysfs-class-power`）只到这一层：

| 取值 | ABI 上的定义 |
| --- | --- |
| `auto` | 正常充电，**并遵循**充电上限 |
| `inhibit-charge-awake` | **仅设备处于唤醒（awake）状态时**禁止充电 |
| `inhibit-charge` | 任何状态下都禁止充电 |

ABI 对 `inhibit-charge-awake` 只界定了"唤醒时禁止"，**并没有承诺**睡眠 / 关机后会发生什么、
更没有承诺这时候还遵循不遵循充电上限——那是各机型驱动自己的实现细节，不能一概而论。

**② F1 Pro 的实际行为**来自 `drivers/platform/x86/oxpec.c`（OneXPlayer EC 驱动，F1 归入 `oxp_fly`）：
该驱动把 `charge_behaviour` 直接映射到 EC 的充电抑制寄存器，并**单独**处理
`charge_control_end_threshold`。在 F1 Pro 上实测表现为：

> 设备唤醒时暂停充电；进入睡眠 / 关机后解除唤醒状态的充电抑制，
> 因此接电时会恢复充电，充电上限由 EC 的 threshold 设置控制。

所以"开机旁路睡眠后会恢复充电并停在设定上限"是 **oxpec + EC 的具体行为**，
不是 `charge_behaviour` 这个 ABI 的通用承诺。换一台用别的驱动实现同一 ABI 的机器，
睡眠后的行为完全可能不同。

下文「充电上限与各模式的关系」那节给出的是 ② 的寄存器级细节（F1 Pro 特有），
不要把那张表当成 Linux 的通用规则。

不改名的话 QAM 里会同时出现两个条目，而它们都会去抢同一个 EC —— 两个控制线程
互相覆盖 `pwm1`，风扇会抽搐。

两种做法选一种：

**A. 先卸载旧插件（推荐）**

```bash
sudo rm -rf ~/homebrew/plugins/"F1 Pro Battery Control"
sudo systemctl restart plugin_loader
```

然后在 Decky 里按上面的方式安装新版。旧设置文件（`~/homebrew/settings/F1 Pro Battery Control/`）
可以直接删掉——新插件用新的设置目录，不会读取它：

```bash
rm -rf ~/homebrew/settings/"F1 Pro Battery Control"
```

**B. 用一键脚本**：`install.sh` 会自动清理旧目录（见脚本里的 `LEGACY_PLUGIN_NAMES`）。
旧设置目录仍需按上面那行手动删。

`test_display.mjs` 不复制前端逻辑，而是**从 `src/index.tsx` 抽取真实表达式**再求值，
枚举各种 `status` / 旁路 / 外接电源组合断言输出文本；风扇面板部分同样抽取真实条件
（控件禁用、不可用降级、曲线编辑守卫、诊断标签）求值断言。所以它同时守住两件事：
显示规则被改坏、以及表达式被改到抽取不到（后者会直接报错而不是默默通过）。

> 写这类断言时注意：**"源码里包含某个判断"不是有效断言**。最初风扇那几条写成
> `includes(...)` / `length > 0`，变异验证时全被证明是空转的（把实现改坏照样通过）；
> 而且同一写法在源码里出现多处时，只替换一处也测不出来。现在一律抽取表达式**跑不同输入**，
> 且多处的写法逐处检查。

`test_backend.py` 用假 sysfs 树模拟内核语义，覆盖写入校验、内核静默忽略写入、内核夹值、
EINVAL、持久化、模拟 Decky 重启恢复、内核不支持时降级、多电池选择、功率符号、
多节点时的外接电源识别（Mains 优先、USB-C 回退、诊断节点名跟随实际在线的节点）等；
风扇部分另外用一个**故意复刻驱动怪癖**的假 EC（手动且 PWM=255 时 `pwm1_enable` 读回 `0`、
写 `0` 会切手动满速、非手动模式写 `pwm1` 不生效）覆盖曲线插值边界、写入死区、
**安全保护绕过死区**（含 85.0 °C 边界与"非安全温度下死区仍然有效"的反向断言）、
外部夺权后自愈、卸载交还 EC、启动残留手动兜底、各条失败回滚路径，
以及**控制权无法确认 / PWM 读回与目标不符**这两条"报成功但没真做"的路径。

`test_display.mjs` 另外覆盖前端的三条界面规则：**曲线不得被 `sort` 重排**
（含"越界节点被判非法"以及反向对照"旧实现的 sort 会制造 PWM 倒挂"）、
**温度滑杆必须夹在左右邻居之间**（直接对抽取出的 `tempBoundsFor` 求值）、
以及**切预设模式要立刻同步本地曲线并清掉编辑标记**。

它还带一节**品牌一致性**断言：改名后 `src/index.tsx` 里不得再出现旧称谓
（`F1 Pro 电池` / `F1 Pro Battery` / `F1 Pro Battery Control` / `电池控制中心`），
且四处用户可见标识（失败通知标题、兜底区块标题、QAM 标题、插件注册名）都用新名。
方向是**双向**的：既验新名在场、也验旧名不在场 —— 只查前者的话，以后有人再添一处旧名照样绿。

`test_backend.py` 的**第 15 节**把上面那两条路径单独成节，逐条断言：
① `pwm1_enable` **读不回来**（`None`）时不得直接写 `pwm1`
（`None` 取非会得到"非自动"，于是夺回控制权被跳过，而 EC 可能根本不在手动模式）；
② `pwm1` 写后**读回必须等于目标**（目标 115、读回 40 必须报错）。
两条都配了反向断言（"读回可辨且为手动时照常写""读回一致时返回读回值"），
防止修完把正常路径也判成失败。

**第 16 节**守 `main.py` 的**日志前缀**：
不得残留旧的电池日志前缀（`F1Pro` + `Battery` 那种写法，`main.py` 里已清零），
且**必须精确等于 5 处新前缀 + 13 处 `F1Pro Fan:`**。
风扇日志有意与主前缀分层（便于在 `~/homebrew/logs/` 里只捞风扇那条线），
这一节就是防止有人"顺手统一"掉。用精确计数而非"至少一处"，
是因为变异验证证明过：`> 0` 的写法删掉其中一条照样绿。

`test_display.mjs` 的**第 13 节**守**轮询背压**：断言轮询用递归 `setTimeout`
而非 `setInterval`、续排写在 `finally` 里（中途抛错不能让轮询静默停死）、
卸载时清理定时器。除了文本断言，还有一条**求值验证** —— 把 `tick` + 调度逻辑
抠出来手动驱动 5 轮，证明**在途 `tick` 恒为 1**、取消后不再续排。
只断"用了 `setTimeout`"是文本匹配，改坏实现照样能通过。

> 断言写完一定要做**变异验证**：把实现改回坏版本，确认对应断言真的变红。
> 本项目的经验是「看起来在测」和「真的在测」差距很大——安全保护绕过死区那条，
> 第一版的"前置"断言取了一个死区恰好放行的温度，结果整条断言空转；
> 后来用插值函数**算准**期望值（84.8 °C → 252）才成立。变异脚本要**全部替换**同名写法，
> 只替第一处会漏掉其余几处。
>
> 前端这次也踩到一次：断言"主页显示转速"时，我把区块切片的正则收得太早
> （`</PanelSection>` 只匹配到第一处），导致断言跑在一个被截断的片段上而恒假。
> **正则切区块要锚到下一个顶层元素**，并让"抽取失败"直接抛错而不是静默通过。
>
> 日志前缀那节同样栽过一次：第一版写 `len(hits) > 0`，变异验证时"删掉一条前缀"
> 直接逃逸（还剩 8 条，仍然 `> 0`）；改成**精确计数**后才抓得住。
> 同理，"风扇函数里不得混用主前缀"那条最初按字符串找函数边界，
> 遇到实例方法（缩进 `    def`）会切错区间而漏检 —— 现在改成对两串前缀分别精确计数、
> 再交叉断言"互不侵占"，逻辑更简单也不会因切片失误而失效。

## 使用

QAM → Decky → F1Pro EC Control：

* **电池状态**：容量，以及 `状态 · 功率 · 上限 N%` 状态行（插电且电池不充不放时状态为
  `供电中`），下方是当前生效的充电模式。
* **充电模式**：三个按钮，当前生效的那个前面会显示 ✓。
* **充电上限**：下拉选择。选「不限制」会写入 100% 解除限制。
* **设置**：控制 Decky 启动时是否自动恢复。
* **诊断**：显示实际使用的电池节点、外接电源节点、内核 `status` 原始值、
  `charge_behaviour` 原始字符串、`power_now` 原始值、上限节点是否存在——
  排查内核差异时把这部分内容发出来即可。

### 关于提示：成功时不弹通知

Decky 的 toaster 除了在右下角弹出，还会把通知塞进 Steam 的通知中心。所以只要每次切换都提示，
通知中心里很快就会堆成一长串「已切换为…」。

本插件**只在操作失败时提示**，而且失败提示**故意保留**在通知中心，方便事后回看错误原因
（失败很少发生，不会堆积）。成功切换不弹任何通知——因为每次写入后后端都会重读内核节点，
界面上的模式和上限本身就是内核里的真实状态，已经起到反馈作用了。

失败通知的标题固定为 **`F1Pro EC Control`**。改名后这里曾短暂残留旧标题「F1 Pro 电池」，
风扇报错时会让用户以为是电池的问题；现已统一，并由测试守住
（见 `tests/test_display.mjs` 的「品牌一致性」一节——它同时断言**新名在场**与**旧名不在场**，
后者才是防止再次漂移的关键）。

### 关于插件目录的属主

`install.sh` 用 `sudo cp` 写入插件目录，因此复制完成后会执行一次：

```bash
sudo chown -R "$TARGET_OWNER:$TARGET_GROUP" "$DEST_DIR"
```

否则文件属主会是 `root:root`。插件自身虽然以 root 运行（`flags: ["root"]`），
但 Decky 还要以普通用户身份去列目录、读资源、做更新与删除，root 属主会让这些操作受限。

属主按三级回退确定（越靠前越准）：`SUDO_USER` → 源码目录的属主（`stat`）→ `$USER`。
**中间那级不是多余的**：脚本若以 root 身份运行（`su -`、systemd 调用），
`SUDO_USER` 和 `USER` 都会是 `root`，这时直接用 `${SUDO_USER:-$USER}` 会静默失效。

### 状态行显示什么

状态行格式为 `状态 · 功率 · 上限 N%`，**功率只在电池确实在充/放电时出现**：

| 显示 | 出现时机 | 示例 |
| --- | --- | --- |
| `充电中 · 45.9 W` | 正在充电 | `充电中 · 45.9 W · 上限 100%` |
| `供电中` | **外接电源在带整机、电池不充不放**：旁路模式（开机旁路 / 始终旁路），或正常充电模式下电池已到设定上限 | `供电中 · 上限 100%` |
| `放电中 · -37.6 W` | 拔掉充电线，或正常充电模式下电池在放电 | `放电中 · -37.6 W · 上限 100%` |
| `已充满` | 充满、电池不再取电 | `已充满 · 上限 100%` |
| `未知` | 读不到内核 `status` | `未知 · 上限 100%` |

`供电中` 把两种来源合并了，因为它们的物理状态完全一样——适配器供整机、电池闲置。
**区别只在"为什么没在充电"**（内核禁止 vs 已到上限），而这个信息就写在其下一行的
「当前模式」里，不需要在状态行重复一遍。所以判据是：
**外接电源在线，且内核没有报充电/放电**。

后三种（`供电中` / `已充满` / `未知`）**不显示瓦数**：这些情况下电池电流≈0，
`power_now` 不再有实时意义，读数往往停留在切换前的旧值，显示出来只会误导。

> 唯一的例外：外接电源**确认已断开**（读到 `online = 0`）却仍报 `Not charging`，
> 这是自相矛盾的读数。此时不硬说成"供电中"，显示 `未充电`——除非遇到硬件异常，
> 这种情况不会出现。

### 状态行里的功率是什么

显示的是内核 `power_now` 的原始读数（单位 µW，插件换算为 W），也就是**电池这一侧**的功率：

* **正值** = 电流流入电池（正在充电），例如 `充电中 · 46.0 W`
* **负值** = 电流流出电池（正在放电），例如 `放电中 · -37.6 W`

> 负号是插件补的：ACPI 电池驱动（`drivers/acpi/battery.c`）会把 `_BST` 的 rate
> 取绝对值（`battery->rate_now = abs((s16)battery->rate_now)`），所以从这个节点读到的
> `power_now` **永远是正数**，方向只能依据 `status` 判断。插件在 `status` 为
> `Discharging` 时补上负号，若内核本来就给了负值则原样保留。

它**不是充电器/适配器的输入功率**。插着电时这个数字通常明显小于充电器端的功率计：
适配器要先供整机运行，剩下的才充进电池。例如实测中充电器端为 62.7 W 时，
电池侧约 46 W —— 差额就是整机功耗。

**要判断旁路是否真的生效，请看充电器端的功率计**（适配器端降到个位数、
≈ 整机空载功耗，就说明旁路成功了），插件里的瓦数在旁路时不显示。

拔掉充电线后旁路自然失去意义，状态行恢复为 `放电中 · -37.6 W` 这样的真实读数。

### 充电上限与各模式的关系（F1 Pro 特有实现，易错）

> 下表和结论都是 **F1 Pro 上 oxpec 驱动的实现**，不是 Linux 通用语义（区别见上文「语义边界」）。

充电模式和充电上限都由 OneXPlayer EC 驱动 `drivers/platform/x86/oxpec.c` 写进 EC 寄存器，
两者是**独立**的，不存在"旁路时上限就失效"这种简单关系：

| EC 寄存器 | `auto` | `inhibit-charge-awake` | `inhibit-charge` |
| --- | --- | --- | --- |
| `0xA4` 充电抑制<br>（bit0 = 唤醒时抑制，bit1 = 关机时也抑制） | `0x00` | `0x01` | `0x03` |
| `0xA3` 充电上限 | 被遵循 | **仅睡眠 / 关机时被遵循** | 永不充电，因此不起作用 |

* **正常充电**（`auto`，抑制位 `0x00`）：`0xA4` 不抑制，充电决定权交给 EC 的上限逻辑，
  充到设定上限后停。
* **开机旁路**（`inhibit-charge-awake`，抑制位 `0x01`）：只置"唤醒时抑制"这一位，
  唤醒期间 EC 不充电；睡眠 / 关机时该位不再生效，EC 按 `0xA3` 的阈值照常充电。
* **始终旁路**（`inhibit-charge`，抑制位 `0x03`）：把"唤醒时抑制"和"关机时抑制"两位都置上，
  EC 在任何状态下都不进入充电流程，因此上限确实没有实际作用。

也就是说，只有「始终旁路」这一种模式下上限才是空转的；正常充电与开机旁路都会被 EC 执行。
插件因此**不**在界面上为上限附加任何说明。

## 风扇控制

风扇与充电由**同一个 EC 驱动** `drivers/platform/x86/oxpec.c` 负责，它注册的 hwmon 设备名是
`oxp_ec`，只暴露三个属性：`fan1_input`（转速）、`pwm1`（占空比 0–255）、`pwm1_enable`。
驱动**没有温度通道**，所以 CPU 温度取自 AMD 的 `k10temp`（`temp1_input`，Tctl）。

节点一律按 hwmon 的 `name` 查找，**不依赖 hwmon 编号**——编号会随内核版本和驱动绑定顺序变化
（`hwmon4`/`hwmon5` 可能变成 `hwmon3`/`hwmon7`）。

### 界面

* **主页**按 `电池 → 充电模式 → 充电上限 → 风扇 → 设置 → 诊断` 单页滚动排列。
  风扇区块直接给：CPU 温度 / 转速 / **当前 PWM**、当前模式与控制方式，
  以及**五个模式按钮**（自动 / 静音 / 均衡 / 性能 / 自定义）——
  打游戏时想换曲线档位不必先进子页面。
* **五个模式按钮每个独占一行**，宽度与「编辑风扇曲线」一致。
  这里**刻意不用网格**：两列平铺在真机上先后踩到两个坑 ——
  裸 `1fr` 时 `ButtonItem(layout="below")` 内部的 min-content 宽度会把列撑破、
  整行超出 QAM 面板（最右侧按钮被裁掉）；改成 `minmax(0, 1fr)` 后不再撑破，
  但**相邻两个按钮的底色块会互相重叠、文字叠在一起**。
  `ButtonItem` 内部还有一层插件控制不到的宽度约束，所以不再和它较劲。
  测试里有一条反向守卫：整个源码中不得再出现 `gridTemplateColumns` 或网格样式常量。
* 只有**编辑曲线**才进独立子页面。子页面**不再重复展示风扇状态与风扇模式**
  （主页已经有了），进去直接是五点曲线编辑，然后是
  **「保存为自定义并应用」**，最后是**曲线预设**（应用静音 / 均衡 / 性能曲线 +
  **还原默认曲线**）。
* **预设按钮只是把曲线载入滑杆，不直接写 EC**。此前点「应用静音曲线」会切到
  *静音模式*（EC 按预设跑），但滑杆上还是原来那条曲线 ——
  用户看到的和实际在跑的不是一回事。现在预设只填滑杆值，让用户看清这条曲线
  长什么样、还能接着微调；真正生效统一由「保存为自定义并应用」完成。
  「还原默认曲线」同理，只是把后端给出的默认种子曲线填回滑杆。
* 页面切换用的是插件内部的 `view` 状态，**没有引入 Decky Router** —— 一个子页面不值得
  多一层路由依赖。
* 曲线用 5 组滑杆编辑（每组一个「温度」+ 一个「PWM」），不依赖图表 / 拖拽库。
  真正的二维曲线图属于后续可选项，当前版本优先保证控件行为稳定可预期。
* **温度滑杆夹在左右邻居之间**：每个节点的可用范围是 `[左邻居+1, 右邻居-1]`，
  边界直接写在滑杆标签上。越界值**滑不出来**，比滑完再报错体验好；
  相邻节点贴到一起时该滑杆会自动置灰。
* **曲线顺序错了就报错，绝不自动重排**：早期实现会把节点按温度 `sort` 一遍再保存，
  于是用户把节点 1 从 40°C 滑到 55°C、越过节点 2 的 50°C 之后，
  曲线被静默重排成 `[50°C, 75] / [55°C, 40]` —— 温度是递增了，但 **PWM 倒挂了**
  （45°C 给 40、50°C 给 75），等于悄悄改乱了用户的设置。现在改为**按原样校验递增性**，
  不合格就提示并拒绝保存，不替用户猜。
* 拖动滑杆时**不会被 5 秒轮询覆盖**：只有用户没动过曲线时才把服务端值同步到界面，
  否则轮询会把拖到一半的滑杆拽回旧值。
* **切预设模式时本地曲线立刻跟着换**：点「静音 / 均衡 / 性能」会同步把滑杆设成该预设的
  节点值，不必等下一轮轮询（最长 5 秒）才看到变化。切「自动 / 自定义」时不动曲线——
  自动没有曲线，自定义的曲线交给服务端回填，本地擅自改会覆盖用户正在编辑的内容。
* 风扇不可用（机型没有这些节点、或驱动身份无法确认）时，整块**降级成一行原因**，
  **不会摆一排点不动的按钮**，也**不会每 5 秒弹一次错误**。
* 点「保存并应用」会先保存曲线、再切到「自定义」模式；这样曲线一定是生效的，
  而不是"存了但没在用"。
* 预设按钮（静音 / 均衡 / 性能）的作用是**把风扇切到该模式**，不是把曲线复制成自定义。

### `pwm1_enable` 的取值是驱动相关的（易错）

| 写入值 | `oxpec`（本机） | 旧驱动 `drivers/hwmon/oxp-sensors.c` |
| --- | --- | --- |
| `1` | 手动 PWM | 手动 PWM |
| `2` | **EC 自动控制** | `EINVAL` |
| `0` | **切手动并把 PWM 拉到 255 满速** | **EC 自动控制** |

写错不会报错，但会让 EC 卡在手动满速。因此插件**先确认本机驱动身份**（电池节点上是否有
`charge_behaviour` / 充电上限，这是 oxpec 独有的）才允许写风扇；确认不了就禁用风扇写入，
宁可不控制也不猜。

这道门禁**每一步都查**，不只是入口查一次：控制线程会在后台长时间运行，期间硬件判据可能
变化（电池节点消失、驱动被替换），所以 `_fan_step()` 本身也重新确认一次——写错
`pwm1_enable` 是静默的，多查一次的成本远低于把 EC 留在手动满速的风险。

还有一个**读回陷阱**：驱动读 `pwm1_enable` 时，手动模式下且 PWM 恰好为 255 时**返回 `0` 而不是 `1`**
（`Return 0 if at full fan speed, 1 otherwise`）。所以判断"是否处于手动"必须接受 `{0, 1}`，
只认 `1` 会在风扇满速时把已成功的操作误判为失败。

### 行为约定

* **自动**：交还 EC，写 `pwm1_enable = 2`。
* **静音 / 均衡 / 性能 / 自定义**：写 `pwm1_enable = 1`，此后按「CPU 温度 → 五点曲线 →
  线性插值 → PWM」每 3 秒调整一次。
* **写入死区**：只有目标 PWM 与当前 PWM 的差值 ≥ 8 才真的写 EC，否则温度抖动会不停写寄存器。
  死区**只作用于曲线插值的结果**，不会拦截下面这条安全保护。
* **安全保护**：CPU 达到 **85 °C** 一律满速 255，**任何自定义曲线都不能覆盖它**，
  并且**无条件写入、不受写入死区约束**。理由：安全阈值附近曲线插值本身可能已经很高
  （例如 84.8 °C 插值出 252），跳到 85 °C 时目标 255 与当前值只差 3，会被死区挡下；
  而只要插值结果仍在 250 附近，之后每一轮都会继续被挡——风扇永远到不了满速，
  安全保护形同虚设。写一次 255 的开销远低于让 CPU 在 85 °C 以上吹不到满速。
* **控制权自愈**：如果 EC 或其它工具把 `pwm1_enable` 改回自动，插件下一轮会重新切回手动
  （否则继续写 `pwm1` 是无效的，界面会显示"手动"但实际是自动）。
* **失败也必定交还 EC**：切换模式或曲线时任何一步出错，都会停掉控制线程、把
  `pwm1_enable` 写回 `2`、并把保存的模式改回「自动」。绝不留"已写入手动 PWM 但没有
  任何东西在控制它"的状态——那比直接交给 EC 危险。保存的模式也一并改回自动，
  否则下次启动还会照着手动模式再恢复一次。
* **失败路径同样要过门禁**：控制线程的异常分支**不自己写** `pwm1_enable`，而是统一走
  `_fan_fail_safe()`，由它重新查一次驱动身份。原因是异常来源之一就是门禁失效本身——
  那一刻驱动身份已无法确认，而 `pwm1_enable` 的取值语义是驱动相关的，再写 `2` 有可能被
  其它驱动解释成手动。门禁失效时 fail-safe 不写任何风扇节点，这正是需要的语义。
* **交还 EC 时不做"看起来已经是自动"的提前返回**：`sysfs` 读回可能滞后于 EC 寄存器，
  只凭一次读回值就跳过写入，会把风扇留在手动状态。一律写出期望值再确认；
  多写一次「自动」是幂等的，代价远小于漏写。
* **夺回控制权后要确认**：发现 EC 已收回自动并重新写 `pwm1_enable = 1` 之后，必须
  `_wait_for` 确认真的回到手动。写入被静默忽略时，不确认的话后续 `pwm1` 写入全是空转
  ——界面显示手动、温度也在读，但 PWM 根本没生效。
* **交还 EC 的时机**：切回「自动」、插件卸载、以及**插件启动时发现 EC 被留在手动**。
  最后一条是安全兜底：上一次插件崩溃或被 `kill -9` 时卸载钩子不会执行，EC 会停在手动 PWM，
  那种状态下风扇不跟温度走、85 °C 保护也失效，所以启动时无条件纠正——**不受「启动自动恢复」
  开关影响**。
* 自定义曲线为五个 `[温度 °C, PWM]` 节点，温度必须**按原样严格递增**（乱序会报错，
  不会自动重排）；范围 30–100 °C / 40–255。
  「自定义」的初始曲线只是可编辑的起点，**不是推荐曲线**。
* **最低 PWM 是 40，本插件不提供完全停转（0 PWM）**。即使温度低到 30 °C，
  曲线下限也是 40 —— 所以看到「30 °C → PWM 40」是**设计如此，不是 bug**。
  这么做是考虑到掌机在低负载下仍需基础风量带走内存/供电模块的积热，
  而 F1 Pro 的 EC 在 0 PWM 时的行为不完全可控。需要散热彻底停转的话，
  请切回「自动」交给 EC 自己判断。
* **校验失败不会碰控制状态**：节点温度填重了只是提示"不能重复"，风扇继续按旧曲线跑——
  用户可能正在手动模式下调曲线，不该因为填错一个数就把控制权交还 EC。
  只有"应用"环节失败才走上面的交还 EC 兜底。

## 关于 root 标记（重要）

`plugin.json` 的 `flags` **必须是 `["root"]`**。

官方模板 `decky-plugin-template` 的 plugin.json 至今写着 `"flags": ["debug", "_root"]`，
而这是一个自 2022 年首次提交起、**四年从未修正**的过时写法：decky-loader 整个仓库
（含全部历史与分支）都不存在 `_root` 这个 flag。真正决定降权的地方是精确字符串匹配：

```python
# backend/decky_loader/plugin/sandboxed_plugin.py
setgid(UserType.EFFECTIVE_USER if "root" in self.flags else UserType.HOST_USER)
setuid(UserType.EFFECTIVE_USER if "root" in self.flags else UserType.HOST_USER)
```

写成 `_root` 不会报任何错，但插件进程会被 setuid 到 `deck`（uid 1000），
对 `/sys/class/power_supply/*` 的所有写入都会 EACCES。症状很有迷惑性：
**界面正常打开、状态也读得到，但每次切换模式/上限都失败**。

真实需要 root 的插件用的都是 `["root"]`（例如 SimpleDeckyTDP、DeckMTP）。
本插件启动时会把实际 uid 写进日志，`uid=0` 才算正确。

## 日志位置

插件日志（Decky 自动清理，只保留最新 5 个按时间命名的 `.log`）：

```bash
ls -lt ~/homebrew/logs/"F1Pro EC Control"/
tail -n 150 ~/homebrew/logs/"F1Pro EC Control"/*.log
```

Decky 本体日志（加载失败、插件崩溃会出现在这里）：

```bash
journalctl -u plugin_loader -b --no-pager | tail -n 200
```

排查时把这两处的内容一起发出来即可。

## 故障排查

| 现象 | 原因 / 处理 |
| --- | --- |
| 界面显示"未找到支持充电控制的电池节点" | 内核没有 `charge_behaviour`，需要带 oxpec / 充电控制驱动的内核 |
| 三个模式按钮都是灰的 | 看诊断区的 `charge_behaviour` 原始字符串，确认内核支持哪些取值 |
| 上限下拉框是灰的 | 没有 `charge_control_end_threshold` 节点 |
| 提示"没有权限写入电池控制节点" | `plugin.json` 的 `flags` 里没有 `"root"`（写成 `_root` 不生效），或插件不是通过 Decky 加载的。详见「关于 root 标记」 |
| 提示"内核拒绝了写入" | 内核/EC 不接受该值，报错会带上具体 errno |
| 改了上限但电量还在涨 | 开机旁路在睡眠 / 关机时仍会充电（F1 Pro oxpec 行为），属正常；只有「始终旁路」才完全不充电 |
| 旁路接电时看不到瓦数 | 预期行为：`供电中` 不显示数字，请改看充电器端功率计 |
| 插着电、已到上限时显示「供电中」 | 预期行为：适配器在带整机、电池不充不放，与旁路接电是同一种物理状态 |
| 显示「未充电」 | 罕见兜底：外接电源节点报已断开、内核却仍报 `Not charging`。核对诊断区的「外接电源」与 `status` 两行 |
| 显示「已充满」但上限不是 100% | 内核把"已停在上限"报成了 `Full`（而不是 `Not charging`）。看诊断区 `status` 确认 |
